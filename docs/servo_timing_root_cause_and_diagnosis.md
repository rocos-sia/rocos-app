# UDP 伺服节拍问题：原因、排查与修改结果

记录日期：2026-11-11。对应周期通信实现提交：3df78f7。

本文整理此前在线实验，不代表重新执行测试。完整原始报告位于
build/communication_cycle_20261111_001/report.md，旧版对照位于
build/communication_timing_20261111/report.md。这些构建目录不随 Git 分发，
因此本文保留主要证据、指标定义和后续排查方法。

## 1. 现象与结论

原来的客户端每隔名义 1 ms 发送指令，App 则由主站控制周期唤醒并读取最新目标。
两套节拍独立运行，发布时刻相对控制取用时刻持续移动，接近边界时容易受网络、
调度和锁竞争影响，造成某些控制周期仍使用旧指令。

当时两端抓包显示指令全部到达，但 App 仍触发通信比例保护。这里的“成功比例”
是控制周期取得新指令序号的比例，不是 UDP 到包比例，也不是驱动执行确认。

另一个独立现象是报文出现 2～3 ms 的成批交付。改为周期主动推送后，相位持续
漂移明显改善，但这类突发仍然存在，其具体物理路径尚未唯一定位。

| 问题 | 判断 | 依据 |
| --- | --- | --- |
| 独立发送节拍与控制取用相位不协调 | 已定位并修改 | 旧版发布相位持续移动，边界附近密集重复取用；新版无持续单向移动趋势 |
| 状态快照等下一条输入包才回复 | 已定位并修改 | 快照完成到状态出站 P99 从约 1003 µs 降到 21 µs |
| 接收、发布与控制边界竞争 | 已观察到改善 | recv 返回到获得发布锁 P99 从约 16.13 µs 降到 0.36 µs |
| 毫秒级成批收包 | 仍待定位 | 新版仍有 7 次接收间隔突发，最大 3.368 ms |
| USB 网卡是否是唯一根因 | 证据不足 | 本轮没有同时采集 USB URB 和对方 IRQ/NAPI 路径 |
| 小时级和运动状态下的稳定性 | 本轮未验证 | 对照实验是 30 秒当前位置保持通信测试 |

## 2. 原来的工作方式

~~~text
客户端自己的定时器：每隔约 1 ms 发送
                         ↓
App UDP 线程：接收并发布最新目标，回复最近完成的状态
                         ↓
App 控制线程：按主站节拍读取共享目标
~~~

需要区分三个时刻：客户端发送、App 发布完成、控制线程取用。是否赶上本周期，
取决于指令能否在取用前发布，而不仅取决于客户端平均发送频率。

下面是说明边界效应的示意，不是原始测试中的具体帧：

| App 一侧时刻 | 事件 |
| --- | --- |
| 10.000 ms | 控制线程使用指令 100 |
| 11.000 ms | 指令 101 尚未发布，控制线程再次使用 100 |
| 11.010 ms | 发布指令 101 |
| 11.990 ms | 发布指令 102，覆盖最新目标 |
| 12.000 ms | 控制线程使用 102 |

101 和 102 都收到了，但一个周期重复旧目标，101 也没有被单独取用。
最新目标策略不会排队补执行旧参考，提前多收一条指令不能给未来周期“充值”。

## 3. 相位漂移的数学解释

在统一的观察时间轴上，简化写成：

\[
t_k=t_0+kT_r+\eta_k,\qquad
p_n=p_0+nT_c+\epsilon_n.
\]

- \(t_k\)：App 实际控制取用时刻。
- \(p_n\)：App 指令发布时刻。
- \(T_r,T_c\)：控制与指令发布节拍的平均周期。
- \(\eta_k,\epsilon_n\)：控制唤醒、网络交付、线程调度等抖动。

即使两端都配置 1 ms，平均周期仍可能略有差异。忽略抖动时，对应序号的相对时刻
含有 \(n(T_c-T_r)\) 项，误差会随运行时间累计。上述表达是分析模型，不要求直接
比较两台机器未经同步的单调时钟。

当目标原本提前几百微秒准备好时，几十微秒抖动通常不会影响取用；当发布相位移动
到取用边界附近，同样的抖动就可能让一个周期读到新目标、下一个周期又读到旧目标。
慢速漂移将系统带到边界附近，局部抖动和竞争使它反复跨越边界。
不能仅凭平均频差解释全部重复周期。

实验使用真实取用时刻计算相位。对每次发布就绪时刻 \(p_n\)，找到：

\[
t_k\le p_n<t_{k+1},\qquad
\phi_n=\frac{p_n-t_k}{t_{k+1}-t_k}.
\]

每秒计算圆均值，跨秒展开后拟合；每个拟合块至少包含 500 个样本，排除收尾短块。
相位归一到名义 1 ms，0 和 1000 µs 均为控制边界。对照使用锁内
ready_ns 作为发布就绪点，实际共享目标对另一线程可见还需要解锁；
published_ns 是解锁后采集的时间，两者不是同一个事件。

旧版拟合约 -128.14 µs/s，平均相位约从 679 µs 移动到 49 µs；
新版本次 30 秒拟合约 -0.25 µs/s，每秒均值约在 241～346 µs 内波动。
负号表示所用相位坐标的变化方向，不是负网络延迟。
新数值不是长期漂移上界或硬实时保证。

## 4. 通信保护为什么会触发

完整窗口为最近 100 个控制取用周期。令：

\[
I_k=\begin{cases}
1,&\text{本周期读取的序号不同于上周期},\\
0,&\text{本周期仍读取旧序号},
\end{cases}
\qquad
R_k=\frac{1}{100}\sum_{i=k-99}^{k}I_i.
\]

success_rate=0.89 表示该窗口中 89 个周期读到新序号，11 个周期没有。
它不等于 11% 的 UDP 报文丢失。

missing_cycles 是当前连续没有新指令的周期数；新指令出现后归零，但前面的缺帧
仍留在滑动窗口内。因此 success_rate=0.89、missing_cycles=0 并不矛盾。

当前源码默认 minimum_success_rate=0.90、low_quality_cycles=100、
max_missing_cycles=20。实际运行取有效配置；此前讨论的 30 并未在这轮实施。
比例低于阈值需要持续达到配置的低质量周期数，连续缺帧、接收超时、
控制线程超时则还有其他保护路径。多个滑动窗口高度重叠，不能把它们当作
互相独立的 100 帧样本。

统计按真实控制调用逐次记录，另外累计经过的名义周期和不足一周期的余数。
它不会把主站实际较慢的每一小段周期偏差都伪造为一次网络缺帧。
应同时观察控制周期耗时、序号覆盖、连续缺帧和单调时钟接收超时。

## 5. 旧版状态回复的额外等待

旧版收到指令后，才回复最近完成的快照。周期 \(k\) 的状态可能已经准备好，
但仍需等下一条输入包触发发送。客户端获得反馈的时间因而也随发送相位变化。

实测快照完成到状态出站 P99 为 1003.256 µs。
控制线程取用到周期完成的 P99 约为 43.139 µs，没有证据表明主要问题是
控制计算本身占满 1 ms；等待发送和实际计算是不同阶段。

## 6. 修改后的周期驱动方案

~~~text
App 完成周期 k，发布一致快照
  → 非阻塞 eventfd 通知原 UDP 线程
  → UDP 线程主动发送最新状态
  → librocos 接到新的 cycle/sample_time_ns
  → 执行一次回调并立即发送一条指令
  → App 发布目标，等待后续控制取用
~~~

控制线程不执行 socket 发送或等待客户端。客户端正常控制阶段取消独立的
1 ms 发送定时，不再积累自己的发送相位；启动查询仍可使用名义周期。
新状态触发一次响应，重复/冻结状态不推进指令序号，积压状态与通知只取最新值，
最终指令只发送一次并等待应用序号确认。丢一帧后 App 后续仍主动推送，
避免双方都等下一条报文。

如果希望周期 \(k\) 的反馈对应的指令赶上 \(k+1\)，需满足：

\[
C_{\mathrm{send}}+D_{\mathrm{down}}+C_{\mathrm{callback}}
+D_{\mathrm{up}}+C_{\mathrm{publish}}+M<T.
\]

其中 \(T\) 为实际控制周期，\(M\) 为取用前裕量。200 µs 只是当时提出的观察目标，
不是新增强制阈值。当前没有预约执行周期或未来轨迹队列，下一周期应用仅在预算
满足时成立。网络往返、回调和调度超时仍会导致迟到。

首点、会话/IP/端口、序号、反馈、导数及通信保护继续执行；
查询和状态推送不刷新运动看门狗。App 和 SDK 必须配套更新，即使 UDP v2
二进制布局没有变化，旧版仅回显 App 也无法满足新版 SDK 的周期响应要求。
applied_message_id 仍表示硬件接口提交参考，不是驱动实际执行确认。

## 7. 在线对照结果

两轮都使用 communication_test.cpp 保持首次收到的 q_d，没有执行轨迹运动。
本机为 r8152/RTL8156B USB 网卡，对方为 e1000e 网卡。
本轮没有调整滤波、限速、J=10000、网卡或线程优先级。
客户端 RR30，App 控制 RR20、UDP RR20、监督 RR21。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 实际测试结果 | 约 5.644 s 后保护停止 | 30 s 正常结束 |
| 完整 100 周期窗口最低覆盖 | 0.81 | 0.98 |
| 全程新指令覆盖 | 99.3623% | 99.9633% |
| 发布相位拟合趋势 | -128.14 µs/s | -0.25 µs/s |
| 快照完成到状态出站 P99 | 1003.256 µs | 20.993 µs |
| 接收返回到获得发布锁 P99 | 16.134 µs | 0.360 µs |
| 控制取用到周期完成 P99 | 43.139 µs | 36.517 µs |
| 对方接收间隔最大值 | 3.436 ms | 3.368 ms |

新版有 30002 条正序号指令，两端抓包及接收诊断完整对应并全部正常发布。
30008 条状态在两端对应，抓包丢弃为零，诊断环未覆盖。
运行中 10 个重复取用周期与 7 次接收突发对应，另有 1 个正常收尾等待周期。
部分目标被更高序号覆盖，不能称为丢 UDP 包。

新版已被取用指令的发布到首次取用 P1/P50/P99 为
524.158/712.292/835.074 µs。这是目标准备好后到取用的等待间隔，
不能解释成执行器计算耗时。有 2 条不足 200 µs：启动首帧及一次突发后的指令。
因此并非每帧都满足 200 µs 裕量。

两轮时长、初相位和突发次数不同，属于顺序对照，不是随机交叉 A/B。
前 5.644 秒旧版有 36 个无新序号周期，新版为零，但新版该短区间没有发生接收突发，
不能把该局部改善全部归因于软件修改。30 秒静止通信结果不能证明小时级运动稳定性。

## 8. 尚未解决的成批收包

新版 7 次接收间隔超过 1.5 ms，最大 3.368 ms；对应本机出站间隔约 0.999 ms。
这说明软件节拍协调之外，内核出站抓包点到对端入站交付路径仍存在突发延迟。
出站抓包时间不是网卡实际发上网线的硬件时间戳。

目前不能唯一归因于 USB 驱动、USB 传输、线路、中间设备或对方 IRQ/NAPI。
提高 UDP 线程优先级只能改善用户线程被唤醒、竞争 CPU/锁等阶段，
不能让尚未交付到对方内核的报文提前出现。

## 9. 排查方法和判定标准

保持 J=10000、算法、保护阈值和已验证节拍方案不变，先只做当前位置保持通信。
不要用主动运动掩盖通信问题，也不要通过放宽保护阈值来替代定位。

### 9.1 同时保留哪些证据

| 证据 | 用途 |
| --- | --- |
| 两端 UDP 抓包与抓包丢弃计数 | 区分没有发送、途中丢失、迟到交付和抓包漏记 |
| UDP message_id、会话 ID、报文负载 | 精确关联同一条指令，避免只按近似时间配对 |
| 控制 cycle、consumed/reference/applied_id | 区分收到、生成参考和硬件接口提交 |
| receive/locked/ready/published 时间 | 定位接收返回、发布锁竞争和发布处理 |
| control entry/locked/consumed/completed 时间 | 定位控制唤醒、互斥等待和周期计算 |
| 实际线程策略、优先级和主站节拍 | 避免把请求参数当作已经生效 |
| 诊断环覆盖数、程序和共享库哈希 | 验证数据完整性与实际加载版本 |

诊断使用预分配双环，不逐周期打印。启用方法与导出格式见
[时序诊断说明](servo_timing_diagnostics.md)。优先在会话停止后导出；
每流 65536 条在 1 kHz 下约保留 65 秒，长测应明确覆盖范围。
不能因为应用层诊断没有某条非法来源报文就断言网络未交付它。

### 9.2 如何分段

1. **本机出站间隔已经过大**：检查状态到达、回调耗时、客户端调度与发送调用。
2. **本机出站规则、对方入站成批**：追踪本机 qdisc/驱动提交、USB URB、
   交换或直连链路、对方 IRQ/NAPI，并做原生 PCIe 网卡对照。
3. **对方入站及时、recv 返回较晚**：检查 socket 队列、UDP 线程调度、
   CPU 竞争与内核接收处理。
4. **recv 及时、获得发布锁较晚**：检查共享锁持有区间和实际调度优先级，
   不能简单认定锁内数据复制过慢。
5. **发布及时、控制仍重复旧序号**：关联真实 consumed 时刻、端点/序号拒绝、
   stopping/fault 状态以及同一周期内是否被新目标覆盖。
6. **控制取用正常、输出提交异常**：继续查参考生成、控制器和硬件提交，
   不把该问题计作网络到包延迟。

### 9.3 如何处理时钟和相位

- 同一 App 的 UDP/控制诊断使用同一 MONOTONIC，可以直接比较。
- pcap 常用 REALTIME，与诊断比较前需做同机映射，报告误差范围。
- 当时固定偏移映射的经验尺度约为 ±2.1 µs，边界附近个别帧不能过度归因。
- 两机单调时钟起点不同，不能直接相减得到单向网络耗时。
- 相位必须相对真实取用点重算，不能只用序号乘名义 1 ms。
- 同时看分位数、最大值和逐帧事件；P99 不能证明每一帧满足截止时间。

### 9.4 下一轮如何验证

先重复相同静止工况，覆盖足够长时间和多次接收突发，再逐项对照网卡或调度设置。
每次只改变一个因素，记录最差 100 周期窗口、重复周期、连续缺帧、接收间隔、
发布裕量、控制周期耗时与末态。优先级实验必须核验实际策略，避免 UDP 抢占
持有同一互斥锁的控制线程后反而增加等待。通过后再独立安排运动和小时级测试。
