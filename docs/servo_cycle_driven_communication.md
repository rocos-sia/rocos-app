# 由 App 控制周期驱动的 UDP 伺服通信

问题原因、逐周期统计含义、后续在线对照及剩余排查方法见
[UDP 伺服节拍问题：原因、排查与修改结果](servo_timing_root_cause_and_diagnosis.md)。
本文末尾的“仅离线测试”描述初次实现阶段，后续 30 秒静止通信在线验证见上述文档。

本次仅调整通信时序，使用原 UDP v2 布局、RCI 接口、会话与端点检查。J=10000、滤波/限速、首点和反馈检查、通信成功比例阈值、独立监督及既有线程优先级均保持原配置。

## 时序

```text
控制周期 k 完成
  → 发布周期快照，非阻塞 eventfd 通知
  → 原 UDP 线程发送最新状态
  → librocos 收到新的 cycle / sample_time_ns
  → 回调生成一条指令并立即发送
  → App 发布目标，在下一次控制取用时读取
```

控制线程不进行 socket 发送，也不等待对端。eventfd 仅用于跨线程唤醒，不增加新线程；通知积压时只发送最新快照，避免补发一串旧周期。

首次通过协议、会话和来源检查的零序号查询登记周期推送地址并立即返回当前快照。后续其他端口的查询不能重定向该地址。首次有效正序号运动包仍按原规则确定运动端点，并将周期推送切换到该端点；绑定后其他端点的查询和指令均被拒绝。零序号查询和主动状态推送都不刷新运动看门狗，不计通信成功。

普通正序号指令只发布目标，不立即回显旧周期状态。服务端周期推送独立于后续指令，因此丢一个请求/状态后，下一周期仍有状态，不会陷入“双方互等”。停止/故障后的最后快照保留原 Abort 尽力发送与 HTTP last_control 查询。

SDK 取消独立的本机 1 ms 发送定时。每个有效新周期最多回调并发送一次，重复/冻结状态不推进指令序号；队列中的积压快照只取最新有效项。最终 MotionFinished 指令只发一次，继续等周期状态里的应用序号确认，再执行原有受控停止与确认流程。

SDK 等待 UDP 的单次阻塞不超过约 1 ms，便于响应外部 stop；该等待不触发保持命令重发。接收超时、应用 ACK 本地时间校验、回调超时、有限值/维度检查均继续执行。两主机单调时钟绝对值仍不直接比较。

## 一个周期的预算

若要使用第 k 周期反馈生成第 k+1 周期目标，必须满足：

\[
C_{\mathrm{snapshot}}+D_{\mathrm{down}}+C_{\mathrm{callback}}+
D_{\mathrm{up}}+C_{\mathrm{publish}}+M<T.
\]

T 为实际硬件周期，M 为取用前裕量。200 µs 是后续测量的初步目标，没有新增为强制阈值，也没有把统计 P99 当成硬截止保证。本次没有加入目标周期字段或未来轨迹队列，下一周期取用是预算满足时的预期行为；迟到由原有最新目标策略和安全保护处理。

本改动针对独立发送时钟扫过控制边界的问题，不能保证消除已有 2～3 ms 的网络成批收包；这些突发仍需单独定位。UDP 发送失败仍是尽力交付，不能替代驱动或主站侧保护。

## 部署与验证范围

App 与 librocos 客户端必须配套使用新编译产物。二进制布局不变不代表节拍行为向后兼容；新 SDK 不可连接仍只按运动包回显的旧 App，当前没有节拍能力自动协商，错配会按原超时保护退出。示例无需修改调用方式；`--realtime` 仍只申请原有客户端优先级。App 的时序诊断继续通过 `ROCOS_SERVO_TIMING_TRACE=1` 开启，见 `servo_timing_diagnostics.md`。

离线测试覆盖无输入时周期状态持续推送、查询不充值看门狗、首点与端点绑定、冻结反馈不重发、服务端周期与客户端名义周期不同、丢一帧状态后恢复、最终指令确认、停止/故障，以及独立共享内存假主站上的实际 HTTP/UDP 集成。假主站使用唯一测试 ID，不接触真机 ID 0。

本次仅编译并进行离线测试。未启动、停止或重启现场 App，未执行真机或 MuJoCo 在线运动。测试结果和编译日志存放在 `build/cycle_driven_servo_20261111/`。
